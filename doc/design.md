# Design

The project separates reusable processing choices from recording-specific data. TOML is configuration only: it cannot execute Python or shell commands. FFmpeg handles conversion, silence detection and multipart encoding and ffprobe reads audio duration; both use argument lists. API-supported extensions pass through unchanged for single-part uploads; other decodable containers share the multipart MP3 encoder.

## Configuration ownership

`config.py` resolves a recording configuration into an immutable Job containing one Profile and its model definitions. Recording files own audio/context/language; profiles own stage wiring and outputs; models own API identifiers and editorial prompts. A bare profile name selects a bundled workflow. Explicit profile paths can be relative or absolute; relative paths are resolved by the file that declares them (or the working directory for CLI paths). Everything needed for a run is read and validated before the first API call.

Model file paths are not model identities. Effective content determines cache validity, so relocating equivalent configuration does not inherently invalidate results. A model definition has one stage type; this makes endpoint and result-contract requirements explicit. Stage type can be stated in a profile for readability and must agree with the model definition.

Built-in profiles describe processing: `quick`, `standard`, `reviewed` (default), and `researched`. Recording type and summary purpose are context, so calls, meetings, interviews and voice notes can share workflows. These are the only bundled profile names; custom profiles use explicit paths. Model definitions may select reasoning effort/mode for text stages. Unsupported audio-stage options are rejected locally; provider-specific capabilities still depend on the chosen model.

The graph validator rejects unknown references, cycles, duplicate IDs (including case-only differences), incompatible input types, and unsupported diarization context. It validates all declared stages, including unused ones. Python's `TopologicalSorter` supplies a validated dependency order; runtime execution visits only selected outputs and their ancestors.

## Scheduling

Both primary inputs and references to stage results in context create edges. `user` and `previous` are special context sources, not executable nodes. No order is inferred from TOML table order, and no parallel flags are required.

Within each part, the engine submits all ready nodes concurrently. Parts execute sequentially; summary stages are deferred until all parts are assembled. The thread pool is sized to the required graph, with no user-facing concurrency setting. It collects completed futures and immediately considers newly ready nodes. In reviewed workflows, both initial transcription passes and diarization start together; draft reconciliation waits for all three, followed by verification and final reconciliation. Workers never wait for another worker's future, avoiding dependency deadlocks within the thread pool.

Completed results are added by the scheduler to its results map. Workers read only their already completed dependencies. Each stage writes a separate cache file. OpenAI client construction and creation of the shared temporary upload use locks; independent API requests use separate file handles.

On error, no new stages are scheduled. Already running siblings finish and retain successful caches. Readable outputs are rendered in the profile's declared output order only after the required workflow succeeds. Multiple recordings run sequentially to keep cost and concurrency predictable.

## Requests and provenance

Each stage receives structured JSON containing primary `inputs` and selected `context`. An upstream stage is represented by its ID, type, result, and direct input/context references. Final reconciliation can distinguish the two initially separate listens from verification influenced by the reconciled draft. Shared user/previous-part context remains visible in provenance.

Every transcription pass receives the same current audio part, even when context contains a draft. The draft goes into the prompt as data. Before audio requests, Python compacts reconciliation context into speaker-labelled text, topic, and deduplicated notes; it omits timing, segment indices, tags and cache keys. Transcription/research context retains its text. User documents, provenance and previous-part origin remain intact, with no word clipping. This reduces prompt overhead within the audio model's context window. Text-stage payloads remain fully structured. Diarization receives no prompt. Reconciliation consumes exactly one diarization result to retain an unambiguous timestamp/index coordinate system.

Reconciliation produces turns with source-segment indices, original speaker IDs, notes, and optional assigned names. Naming is an editorial task: clear current-part dialogue can support a self-introduction, a direct address/response, or an explicit user-provided participant/role association. Every part establishes its own mapping; previous-part and draft names are fallible context, never a mapping inherited from A/B labels. Every diarized index must occur exactly once. Spoken segments cannot be replaced by empty turn text. Timed turns and diarization segments must follow start-time order; overlapping speech and interleaved source-index groups remain valid. Diarization starts must be inside the part; ends allow one second of codec/rounding tolerance. Rendering derives elapsed start offsets from the original segments. Distinct IDs remain distinct when assigned names coincide. Summaries must contain a nonempty overview, including when describing a silent recording. These structural checks cannot prove that every spoken word was preserved or interpreted correctly, or that a contextual name association is correct.

Summary has exactly one primary source, explicitly chosen by `parts.source` and combined across the recording before summary runs. Context can clarify vocabulary but is not additional conversation evidence. There is no heuristic fallback source: profiles define data lineage explicitly.

Explicit user spellings, capitalization, names and corrections take precedence over automatic drafts and web findings for the same entity. This is a prompt policy, not a global replacement engine: a similar string can refer to something else. Supplied background never establishes an unspoken agreement or identifies a voice on its own. Conflicting user context remains uncertain rather than being resolved by file order.

Optional research is a separate text stage with the built-in web-search tool. It consumes transcription drafts and user context and supplies fallible background to reconciliation. It cannot be a summary's primary conversation source. The bundled `researched` workflow performs lookup after draft reconciliation so it can focus on unresolved terminology; its results inform the subsequent audio verification and final reconciliation. Summary still consumes reconciliation and original user context only. This avoids mixing source-finding and structured dialogue generation into one opaque request.

Research retains the provider's consulted source URLs and converts URL-citation annotations to ordinary clickable Markdown. It records whether a web call completed, even when the model decides no lookup is needed. The research notes are also a readable output in the built-in profile. Tool-call budgets and reasoning settings are model configuration and part of cache identity. Search freshness is explicit: a cached research stage is reused until its recipe changes or the user requests `--redo research`.

Schemas and data-handling constraints are protocol, maintained in Python. All structured result schemas live in `formats.py`; one stage-to-schema lookup supplies API requests, result validation and cache schema hashes. Editorial choices belong in model prompts. Changing an endpoint or output contract requires an adapter/schema change, not just a different model string.

`i18n.py` defines the curated ISO 639-1 catalog with explicit labels and unclear markers. Configuration validation and CLI choices share it. Effective request rules name the selected language and its unclear marker; those rules are hashed into cache identity, while document labels are used only by local rendering. Compact audio context retains a stable `Unknown` label as scaffolding, not a translated document label; display-only changes cannot invalidate model requests. Source schemas, timestamps, configuration keys and frontmatter keys remain language-independent. Danish/English tests cover behavior; catalog structure checks are not translation or transcription-quality validation for other languages.

## Parts and final assembly

A cached media manifest binds the source SHA-256, media recipe and configured maximum duration to measured duration and contiguous boundaries. Preflight rejects gaps, overlaps, invalid values, and oversized unsplit input. Bundled profiles cap parts at 300 seconds to leave room under the current audio model's output/context limits; this is a heuristic, not proof of complete speech coverage. For a new split plan, FFmpeg searches a short window before each balanced cut for silence. A hard cut is the fallback. Windows argument lists are used; source paths are never shell code.

Multipart uploads are mono 16 kHz, 64 kbit/s MP3. The cap leaves headroom under the 25 MB upload limit; every actual encoded file is size-checked. Encoding happens once per part on first audio demand, under a lock. Separate upload handles permit concurrent requests. An ExitStack outlives all worker futures for the part, then removes temporary audio. Re-running only text stages needs no conversion.

`previous` carries the immediately previous final `parts.source` and compact earlier topics/names. Its complete text and uncertainties reach transcription through the compact representation; its request key remains in cache metadata even though audio prompts omit it. It is omitted for part 1. Upstream changes flow through context hashes into later text stages. The independent diarization branch receives no such context and keeps its own reusable cache. Preflight walks parts in sequence to determine whether API/media work is needed; it never assumes an uncached previous result. Successful part caches survive subsequent failures.

After the last part, Python concatenates text/research, adds part offsets to all diarization times, namespaces speaker IDs, and rebases reconciliation segment indices. Assembly never compares bare A/B labels across different parts. `assembly.py` prepares indexed text units and speaker evidence for `combine`. Its `declared_name` field carries a provisional part-stage attribution, not necessarily a self-introduction. The combination prompt independently checks each local identity/name against the whole dialogue and explicit user context; it can repair a mistaken local attribution without assuming recurring labels identify the same person. The model returns sparse unit replacements, a complete partition of supplied speaker IDs, topic/tags, and consolidated uncertainty notes. Validation rejects missing/duplicate/unknown speaker IDs, merges of two IDs from one part, unknown or duplicate edit indices, and empty replacements. Python applies the plan without removing or reordering units or changing timing. A group's first ID is only its internal canonical representative, not the source part of all its speech. The mapped diarization belongs only to the combined source and its summary rendering; it does not mutate the original diarization evidence or sibling reconciliation outputs. Semantic correctness remains a model-quality question; structural validation cannot prove a wording correction or speaker match. Uncertain matches should remain separate.

The combination plan is cached independently and the full combined result is reconstructed locally for output and summaries. Its cache dependencies are the assembled `parts.source` and, for reconciliation, its diarization evidence. The source recipe retains its upstream and previous-part lineage. Independent additional outputs do not affect combination identity. Recipe keys remain cache metadata, not model payload content. This limits generated tokens and avoids losing turns because a model shortened a long rewrite. Summary still reads the entire combined source. The entire source must fit the selected text model's input window; this implementation does not provide hierarchical summarization or silently discard context. Lower part duration controls per-part requests only. A one-part recording bypasses both collection and the combine API call.

Multipart caches live under `cache/part-NNNN/`; media metadata, combination plans and summaries live directly under `cache/`. Single-part stage caches also live directly there. This is one format with scope-based storage, not alternate cache lookup. `--redo STAGE_ID` applies to every part; `--redo combine` only to assembly; `--redo all` to all required model calls. Media measurements are independently cached.

## Cache identity and durability

A cache record contains the current schema identifier (`CACHE_SCHEMA`), effective request metadata, a validated result, and a generation timestamp with timezone. The filename includes stage ID, API model, and the first 20 hexadecimal characters of a SHA-256 recipe digest. Full metadata is checked when reading, so a mismatching record is not accepted on filename alone. Missing fields or unsupported cache formats are errors with an actionable `--redo` command.

Request metadata includes:

- Stage type, effective model definition, language and protocol/rules version.
- Payload digest, including selected context, prior results and provenance.
- Dependency recipe keys, including the previous part source recipe when selected.
- Original audio digest, direct-upload format or MP3 conversion choice, and conversion version for audio stages.
- Structured-output schema digest for text stages.

The complete effective model definition is included in request metadata. For research, this includes its web-tool budget; its fixed adapter contract is covered by the protocol version. Prompt and reasoning changes invalidate affected stages and their dependants.

Combining dependency recipes with result content detects both changed upstream settings and changed output from a forced rerun. An unchanged forced output with the same recipe leaves dependants reusable. Changes to a stage never invalidate unrelated branches.

The cache intentionally excludes profile ID and output format. Matching stage IDs and requests can share caches across profiles. Readable outputs live directly in the named output directory and use `<audio-stem>.<stage-id>.<format>` for every selected stage/method, independent of API model or part count. Cache filenames retain model IDs and request hashes. Output naming changes do not change model request recipes, and previous output filenames are not searched, moved or removed. A change of profile may replace same-stage documents, retaining history backups.

Atomic writes use a temporary file in the destination directory, flush/fsync, then replace. Replaced content is backed up under history. A per-recording exclusive lock prevents simultaneous processes from mutating the same results directory. The lock is not an audio-file editor lock; audio should remain immutable during processing. File identity, size and nanosecond modification/change times are checked before and after requests and after each part. The complete audio is hashed at startup and again before rendering; this avoids repeatedly reading a large original for every parallel request while rejecting detected changes. Do not edit audio during a run; completed caches cannot be a substitute for an immutable source.

Only the selected output directory's `cache/` is read. Output directories are independent; the engine does not search elsewhere for reusable results or infer generation dates from file timestamps.

Within a run, parsed and validated cache records are reused when their file identity, size, nanosecond modification/change times and request metadata still match. This avoids reading large transcripts twice during preflight and execution while detecting replacements and edits even when modification times are restored. Duration metadata and rendered documents are written only when needed; an unchanged cached run does not change their modification times or create history entries. The process lock is still created and removed each run.

## Verification boundaries

Offline tests validate orchestration and request construction, not language recognition or provider availability. A three-party barrier proves that both initial transcriptions and diarization overlap; dependency tests check the subsequent draft, verification, research and final stages. SDK integration tests use the installed OpenAI package with a mocked HTTP transport, including real request serialization and response parsing. Full CLI tests use real WAV files, FFmpeg/ffprobe, multipart SDK requests and cached reruns without an API key. A separate test splits a WAV larger than 25 MB and validates encoded sizes and durations. Prompt quality and provider/model access still require representative live recordings and an account.

## Preflight and rendering

Preflight walks cached dependencies without model calls. Each check starts with empty traversal state and clears it on success or failure, while retaining reusable parsed cache records. Rechecking a completed pipeline or retrying a failed check cannot leak prior-part context. An unknown upstream result makes downstream stages potentially pending. Required tool/encoder checks, audio duration probing, template loading and output-path checks happen before calls. Selected MP4 manifests are validated even when model stages are pending. Output paths cannot resolve to any input recording selected by the job, including other batch recordings. Templates are exercised with populated standard branches, including timed/untimed turns and actual `None` values for unknown recording times, to catch missing fields and includes early. The CLI constructs the SDK client and checks API-key presence only if at least one stage is pending. A cached duration avoids repeated probing. Cached stage recipes are checked again during execution without reparsing unchanged records.

Recording start time is explicit or inferred from the documented filename pattern with unspecified timezone; otherwise unknown. Full-track duration comes from ffprobe, preferring the first audio stream's duration and falling back to container duration. Python calculates end time and relative turn offsets. Reconciliation and summary produce topic/tags as structured data; templates render YAML frontmatter using JSON-quoted values (valid YAML) and a compact conversation body. Templates affect only rendering, not request recipes.

Output selection is normalized to explicit methods. Standard Markdown documents are always rendered, and a final reconciled source is always saved as both Markdown and SRT. Text/stdout are additional outputs, not replacements. SRT uses the same dialogue view and final mapped diarization as the reconciliation documents; only the final source gets subtitles. Source bounds are rounded to milliseconds and padded ends capped at full-track duration. Consecutive untimed turns evenly divide the available gap, using the latest prior timed end and next timed start or recording edges; a wholly untimed source uses the whole duration. Existing timed overlaps are preserved, not extended by interpolation. No positive millisecond interval means an explicit export error. Document output is written before subtitle output so Markdown survives those errors; all successful stage caches remain reusable. Rendering-only changes require no cache schema or prompt changes.

Optional MP4 output follows document/subtitle rendering and uses the full original audio, AAC audio encoding and black H.264 video with default-enabled `mov_text` subtitles. Video length is explicitly bounded by recording duration, not the shortest subtitle stream. An event sweep flattens overlapping subtitle cues into non-overlapping intervals containing all active speech, preventing FFmpeg from shortening earlier cues; standalone SRT is unchanged. A local video manifest stores audio, dialogue/timing and rendering recipe identity plus the output checksum. It is independent of model-stage caches and lets unchanged video skip media tools. Each pipeline checks the checksum once and reuses that verification only while the manifest identity and complete file fingerprint still match. Encoding uses a destination-local temporary MP4, validates stream codecs/disposition and full-track audio/video duration, checks source immutability and backs up the old video before atomic replacement. Failed encoding leaves the previous video, documents and model caches intact.

Playback duration is measured from the byte count of decoded mono 16 kHz, 16-bit PCM, streamed and discarded rather than stored as an audio copy. The separate source-bound decoded-duration manifest avoids repeating this work. It corrects bitrate-based metadata estimates without changing existing cached request part boundaries or invalidating paid results. Rendering uses the exact duration for frontmatter, SRT edge interpolation and MP4 bounds; subsequent non-MP4 runs reuse the correction. New AMR probing also uses decoded sample duration. Decoder errors are fatal, not interpreted as early end-of-recording. MP4 validation reports stream type, actual duration, expected decoded duration and signed difference.

One rendering module owns speaker labels, timestamps, summary sections, and frontmatter. A shared dialogue view supplies participants to both reconciliation and summary; labels are disambiguated across declared names and fallback labels, including names that resemble an already disambiguated label. Distinct IDs remain separate. Tag normalization uses Unicode NFC and preserves combining marks rather than stripping meaningful parts of non-Latin words. Markdown labels escape the opening bracket because a short `[time, speaker]: word` line can otherwise become an invisible link definition. Text output uses literal brackets.

Progress is serialized to stderr, keeping stdout usable for documents. Single-part runs omit part headers and prefixes. Multipart runs report each part's elapsed audio range once, followed by ordinary stage lines. The scheduler owns one completion counter for the whole recording: per-part stages, final combination when needed, and final summaries. Both cache hits and successful calls advance it once; failed stages do not. Cached stages have one `Cached` line, while model calls have a `Running` line and a numbered `Finished` line with elapsed time. The counter resets for every recording/run and does not depend on the preflight estimate of pending calls. Output writes distinguish saved from unchanged files. Failed structured responses are retained for inspection. Configuration and ordinary processing failures produce short actionable messages rather than tracebacks. Incomplete and refused responses retain the full provider response as a diagnostic, including any partial output. A refusal is rejected even when the same response also includes output text.

Provider input/output token usage is carried outside structured result fields and retained as optional top-level cache metadata. Raw audio responses can also retain their provider usage fields, but these are excluded from all downstream inputs and previous-part context. Usage-only changes therefore do not invalidate dependants. Older downstream caches whose effective requests included usage have different request hashes and may require a one-time rerun; audio-stage caches remain reusable, and prompt/cache schemas are unchanged. The adapter captures usage for audio, text and research responses and attaches known usage to incomplete/refused/invalid-JSON diagnostics. A lock-protected recording counter records returned usage before result validation or writes, preserving counts even when a later operation fails. The scheduler appends per-task usage after successful completion; cached tasks show `tokens -` and never add their original usage to current-run totals. Missing or duration-only usage is explicitly unavailable; malformed token counts raise a diagnostic warning rather than becoming zero. Completion or stopped-run reporting includes known input/output totals and the number of calls with unavailable usage. Provider cached-input/reasoning breakdowns are subsets of the reported totals, not additional tokens. SDK-hidden retries and unreturned usage cannot be reconstructed or treated as billing truth.
